# dsh-dev-workflow

本文件是插件随包发给每个安装者的默认规范。它按需读取——以下内容都不是常驻上下文。

**你所在的仓库优先级高于本文件。** 它自己的 `AGENTS.md`、`CONTRIBUTING.md` 或贡献者指南若与这里
不同——分支前缀、提交类型、CHANGELOG 标题、评审规则——照那个文档办，把本文件当兜底。凡插件会
强制执行的规则，真正生效的是对应的配置项，引用这里的数字之前先看配置项的实际值。

## 怎么读这份文档

这里同时对三种角色说话；分清一条规则是写给谁的，才不会把约定当成门禁：

- **插件自动执行。**「自动触发时机」与「安全操作规范」描述的是「无论有没有人记得都会
  发生」的行为。不要把这些规则再复述给用户，守卫已经替他们回答了。
- **AI 助手必须遵守。** 本文大部分是给「实际动手的那个人」的指令集，而那个人通常是
  替人类办事的助手。照着做、跑检查、把结果给用户看。
- **人类做决定。** 任何离开这台机器的动作、任何不可逆的操作、以及所有写着「问用户」
  的判断，都归他们。

一个仓库里的规则通常由三份文档承载，它们不能互相替代：

| 文件              | 装什么                                    | 常驻 |
| ----------------- | ----------------------------------------- | ---- |
| `AGENTS.md`       | 每轮都必须成立的稳定规则                  | 是   |
| `CONTRIBUTING.md` | 面向「为这个仓库做贡献的人」的展开版      | 否   |
| 本文件            | 插件随包发给每个安装者的默认规范          | 否   |

文件名不必相同——`CLAUDE.md`、`.cursor/rules`、`docs/` 里的一页都可以。重要的是这个分层：
常驻规则、展开版、以及本文件这份兜底。只有「对任何安装了本插件的仓库都成立」的规则才写在这里；
某个项目自己的命令、CI 布局、发版机制属于那个仓库自己的文档，优先级高于本文件以下任何内容。

角色分工还带来两条交互约定。给建议时只给**一个**主要建议，不要一次摆五个选项——
一列选项等于把决定丢回去，什么也没说。语气跟着利害走：阻塞性问题平实地说一次；
风格偏好提一句就放下。

## 核心原则

- **自动化优于记忆。** 工具能查的规则就该让工具查，而不是靠自觉回忆。任何可机械验证
  的东西都属于 CI 或钩子。
- **原子提交是推荐，不是强制。** 一个提交只解决一个独立的逻辑问题，但「原子」需要语义
  判断，所以它永远不是硬门禁。
- **文档就是代码。** 描述某次变更的文档与这次变更同一个 PR 落地。
- **质量门禁在前。** 类型检查、lint、格式检查与测试在评审之前跑完，评审者读的是意图而
  不是噪音。
- **默认安全，显式确认。** 破坏性操作默认是「问」而不是「放行」。别人看得见的动作同理
  ——用户没批准的提交、push、tag、PR、发布。
- **按动作触发，不靠切档。** 用户要提交、建分支、发版时工作流才出现。人会忘记切模式，
  动作不会说谎。
- **其余时候安静。** 不唠叨，也不每轮把规范全文倒一遍。常驻成本只有一行摘要，全文按需
  读取。

## 分支模型（GitHub Flow）

- `main` 始终可发布，且受保护：不许直接 push，一切经 PR 落地，必需检查必须通过。
- 工作在短命分支上进行，从「最新的」`main` 切出：

  | 前缀        | 用途                    |
  | ----------- | ----------------------- |
  | `feature/*` | 新能力                  |
  | `fix/*`     | 缺陷修复                |
  | `docs/*`    | 纯文档                  |
  | `hotfix/*`  | 针对 `main` 的紧急修复  |

- 分支名全小写、kebab-case（与提交信息里的 type、scope 同风格）。名字必须自己说得清：
  `feature/skill-md`、`fix/guard-force-push`，而不是 `feature/stuff` 或 `feature/NewStuff`。
- **分支命名是约定，不是门禁。** 插件里没有任何地方检查分支名，也没有对应的配置项。
  遵守这条规则是因为「它告诉读者这条分支是干什么的」，而不是因为命名不规范会被拦下。
- 一条分支只做一件事。
- 用 `git merge main` 保持同步，不要 `git rebase main`。在 squash merge 下，rebase 会
  重写分支自己的历史，评审者就再也看不出「上次评审之后改了什么」。
- 冲突在分支上解决，永远不在 `main` 上解决。
- 解决合并冲突之后，提交前重跑项目自己的检查——类型检查、lint、测试，用该项目定义的
  命令跑。冲突解决会改变代码的语义，之前那次绿的运行不再覆盖它——不重验就提交，等于把
  合并当成无风险的文本编辑。
- 合并用 **squash merge**，`main` 上每个 PR 对应一个提交，历史保持线性。
- 落到 `main` 的那个 squash 提交，信息取自 **PR 标题**，所以 PR 标题本身必须符合
  Conventional Commits。
- 分支上的提交会被压掉，永远不会出现在 `main` 的历史里。这就是为什么 PR 标题比分支上
  任何单个提交都重要。
- PR 一合并就删掉分支。

### 分支保护

这套模型假定 `main` 的保护写在仓库设置里，不是靠约定。它依赖的规则：

- 禁止直接 push。
- 禁止强推。
- 禁止删除。
- 必须有 PR，且必需的 CI 检查必须通过。
- 合并前分支必须与 `main` 同步。
- 每条评审对话都必须已解决。

是否**还要**一位评审批准，是各仓库自己的决定，不属于这套模型：单人维护的仓库通常关掉
它，因为「没有人评审」本来就不算评审。

这些都不是插件强制的——它们是 GitHub 的设置，没配这些设置的仓库照样会有「自动触发时机」
里那些检查。假定这份清单生效之前，先看仓库实际的保护配置。

### 紧急修复流程

- 从 `main` 切 `hotfix/*`，永远不要从功能分支切。
- 修好后直接合回 `main`。这个模型里没有 `develop` 或 `release` 分支要绕。
- 紧急修复的 `CHANGELOG.md` 条目写进 `[Unreleased]`，与其他变更一样随下一个版本发布。
- 如果问题严重到必须立刻发版，走「撤回已发布版本」那一节，不要另发明一套流程。

## 提交信息规范（Conventional Commits）

```text
<type>(<scope>): <subject>

<body>

<footer>
```

- `scope` 可选，但当变更明显局限在某一处时鼓励写。
- **Subject**：祈使语气（写 "add"，不写 "added"），结尾不加句号，最多 50 字符。subject
  用英文写，以便与按定义就是英文的 `type`、`scope` 保持一致。
- 阈值与接受的 `type` 列表是**配置**，不是本文的常量：`commitCheck.subjectMaxLength`、
  `commitCheck.types`、`commitCheck.requireScope` 都能在设置面板里改，门禁会按改后的值
  执行。在把这里的数字当成规则之前，先跑 `/dev-workflow status` 看当前生效值。
- **Body**：72 字符换行，解释 *为什么*。不要把 diff 已经写清楚的东西再讲一遍。body 与
  footer 可以用英文或中文，但一个项目选定一种就保持下去。
- **Footer**：引用 issue（`Closes #12`），并记录破坏性变更。

  | Type       | 含义                               |
  | ---------- | ---------------------------------- |
  | `feat`     | 新的用户可见能力                   |
  | `fix`      | 缺陷修复                           |
  | `docs`     | 纯文档                             |
  | `style`    | 格式变更，不改变行为               |
  | `refactor` | 既不是修复也不是新功能的内部改动   |
  | `perf`     | 提升性能的改动                     |
  | `test`     | 新增或修正测试                     |
  | `build`    | 构建系统或依赖                     |
  | `ci`       | CI 配置与脚本                      |
  | `chore`    | 不属于以上任何一类的杂务           |
  | `revert`   | 回退更早的提交                     |

- 破坏性变更：在 type 或 scope 后加 `!`（`feat(api)!: ...`），**并且**在
  `BREAKING CHANGE:` footer 里解释清楚。
- footer 必须写成 `BREAKING CHANGE: <说明>`——全大写、冒号后一个空格。带连字符的
  `BREAKING-CHANGE` 是另一个 token，不被识别。
- 50/72 规则不是美观问题。很多工具会截断 subject，而按宽度折行的 body 在终端与 diff 里
  都还能读。

### scope 与示例

scope 命名的是「变了的行为属于哪块」，不是「动了哪个文件」：

| Scope     | 用于                             |
| --------- | -------------------------------- |
| `guard`   | 某道守卫                         |
| `trigger` | 某个触发器                       |
| `check`   | 检查所评估的那些规则             |
| `config`  | 配置 schema 与默认值             |
| `panel`   | 设置面板                         |
| `i18n`    | 词典与 `t()` 用法                |
| `docs`    | 纯文本                           |
| `deps`    | 依赖与清单文件                   |

一次变更横跨两个领域时，通常该拆成两个提交；确实拆不开时，选用户会注意到的那块写进
scope，另一块在 body 里说明。

同一个变更，两种写法：

```text
fix: 修复崩溃
```

```text
fix(guard): 强推规则不再匹配 git push --force-with-lease

此前规则比较的是原始参数列表，于是安全写法与危险写法命中同一分支，
每次 lease push 都会弹审批。

改为匹配确切参数，同时保持对 `--force` 的覆盖。
```

第二种不打开 diff 就能评审。第一种根本无法评审。

### 引用 issue

- 该开 issue 的时机：问题是真的，但这次不修——推迟的缺陷、需要先达成一致再动代码的提议、
  横跨多次改动的发版清单。issue 的作用是不让这些事只留在「当时听过的人」的记忆里。
- 不要为「这次会话就能做完」的事开 issue。提交信息与 PR 描述已经是那份记录；再抄一份
  等于多一处需要同步的地方，代码一动它就过期。
- **绕过**——本该拦住却没拦、或能不留痕迹地跳过的规则——是缺陷，可以直接开公开 issue。
  这个插件不是安全边界，绕过不是漏洞，公开之后别人才搜得到、补得上。
  例外只有一种：报告里要贴真实凭据，那就先把值换掉再开，否则等于亲手完成一次泄漏。
- 然后在提交里引用它：`Closes #12`——本次提交落地后，issue #12 可以关闭。
- `Refs #12`——本次提交与 issue #12 相关，但不关闭它。
- 多个 issue：`Closes #12, #15`。
- 只写编号，不写完整 URL：仓库已知，而 URL 比它承载的事实更长。

## 原子提交（推荐实践）

- 一个原子提交恰好解决一个独立的逻辑问题，且能用一行意图描述清楚。
- 这是**推荐，不是强制**。原子性依赖语义判断——两处改动该不该放一起取决于意图，而不是
  文件路径——因此它无法机械检查，也永远不是合并阻塞项。
- 准备提交时，如果暂存的改动回答了不止一个问题，或者回退它必须分几步做，就拆开。否则
  保持完整。
- **用户有最终决定权。** 他们要求合成一个提交，就交付一个提交，并把取舍说一次。
- pre-commit 触发器不检查原子性。它只检查可机械验证的部分：提交信息格式、CHANGELOG、
  文档同步。

## PR 流程与质量门禁

提交之前，**把将要提交的内容给用户看，并等他们回答。** 提交是第一件「开始变得难以收回」
的事：说清分支、暂存的文件、提交信息，然后让他们同意、修改或放弃。这是他们的仓库。下面
的清单是「提问之前该核实什么」，不是「可以跳过提问」的许可。

- [ ] 用户看过确切的改动与提交信息，并同意了。
- [ ] 项目自己的检查在本地通过：类型检查、lint、格式检查、测试，用该项目定义的命令跑。
- [ ] 暂存的改动只回答一个问题（见「原子提交」）。
- [ ] 提交信息符合 Conventional Commits。
- [ ] 变更涉及的文档在同一提交或同一 PR 内更新。
- [ ] `CHANGELOG.md` 里有这次变更的 `[Unreleased]` 条目。

PR 描述模板。下面每个小节都必须有内容——缺段或段内为空都会在 `gh pr create` 之前被
拦下。「无」「不适用」或一句话就是完整答案；不被接受的是删掉某个标题、或让它空着，因为
那样评审者分不清「没什么可说」和「没想过」。下面是默认的小节名，门禁按字面匹配，所以
仓库若在自己的模板里改了名，要在 `prSections` 里列出新的名字。其下正文可以用任何语言：

```markdown
## What

给 status 命令加一个 `--json` 选项。

## Why

脚本无法解析当前的散文式输出。

Closes #7

## How to verify

运行 `/dev-workflow status --json`，确认输出可被解析。

## Type of change

Feature：此前不存在的行为现在有了。

## Non-goals

不改人类可读的那份输出。

## Risk and rollback

无；回退这次提交即可。

## Checklist

- [x] 这个 PR 只回答一个问题。
- [x] 去掉这次改动后测试会失败。
```

关于这份模板有两条规则值得在照抄前知道：

- **勾选框默认是空的，勾上才是唯一答案。** 上面示例里是勾好的样子，也就是作者在请求评审前
  留下的状态。门禁会数它读取的每个小节里的 `- [ ]`，所以不适用的行要删掉、并在 Non-goals 里
  说明——为了往下走而勾上，是检查唯一分辨不出的情况。这也是 `Type of change` 写成「删掉不适用
  的行」而不是一组勾选框的原因：四个里勾一个，剩下三个会被数成未勾选，每个 PR 都会被拦。
- **不是每条清单项都适用于每种改动。**「去掉这次改动后测试会失败」对行为改动成立，对文档修正、
  配置默认值、纯重构则毫无意义。那些情况删掉这一行并说明原因——假勾选比删掉更糟，因为它教会
  评审者别再认真看这张表。
- **破坏性变更要给迁移路径**，不只是贴个标签：说清已有调用方需要做什么，写在读者会去找的地方。
- **不要在正文里粘 CI 状态。** 平台会跑检查并把结果挂在 PR 上；手写一句「CI 已通过」是一个
  读到的瞬间就可能过期的声明。

只有在 CI 全绿、分支与 `main` 同步、每条评审对话都已解决时，PR 才可合并。永远不要绕过
失败的检查去合并：修掉原因，或者说清阻塞点。

**两个 PR 同时在飞，一定会在更新日志里撞上。** 两边都在同一个未发布段落下面加行，所以各自
对基线都是干净的，后合并的那个才冲突。开第二个之前先定好合并顺序：先合一个，再 rebase。
闸门会在 PR 创建之前点出冲突的分支与文件——别把它当成随手点掉的警告，那是避免冲突最便宜
的时刻。

**push、打 tag、开 PR、发布，每一个都需要先拿到用户针对这件事的回答。** 它们以用户的
名义离开这台机器，不是助手可以自行完成的步骤。把分支、remote、tag 或版本号，以及确切
命令展示出来，然后等待。一次批准只覆盖那一个动作——同意提交不等于同意 push，同意 push
不等于同意发布。用户还没回答时，状态是「尚未完成」，不是「已完成」。

### 评审者这一侧

上面是作者欠的，下面是评审者欠的。跳过这些的评审，就是在评论上盖了个章。

- 先读标题与 *Why*。在 squash merge 下，标题就是最终留在历史上的提交信息，因此含糊的
  标题是永久缺陷，不是小事。
- 拿 diff 对着声明的意图读。如果 diff 做了描述里没提的事，那就是发现——那部分改动天生
  没被评审过。
- 与它覆盖的代码同处一个提交的测试值得再看一眼：确认断言是跟着新行为移动了，还是被削弱
  以迁就一个 bug。
- 「我信得过」不是一种评审状态。CI 绿且所有对话已解决就批准，否则就要求修改。中间态不
  存在。
- 比起整篇读，更该要求拆分。一个没被读过就批准的 PR，比从未开过的还糟。

### 本地验证与 CI

- 上面的本地清单是推荐，不是硬门禁。
- CI 是硬门禁，不可绕过。它失败时修原因——绝不放宽检查、改 CI 配置绕过去，或用
  `--no-verify` 跳过。
- 如果 CI 设置本身就是错的，开一个 issue，而不是在无关的 PR 里顺手改掉。
- **没跑成的检查不等于通过的检查。** 报成 NOT ASSESSED 并说明原因——没有 git、
  没有网络、文件还不存在。插件自己就是这么做的：它列举文件降级时会明说，
  而不是把沉默当成干净。某条检查根本没执行，就不要写「检查全部通过」。
- **验产物，不验意图。** 声称能用之前先看产出的那个东西——文件在不在、
  命令退出码是不是 0、输出里有没有你说的内容。用流畅的语言描述代码应该做什么，
  不是它真的做到了的证据。
- **第二次失败就停下报告。** 同一个尝试失败两次，不要默默换个写法再来第三次：
  说 BLOCKED，讲清试过什么、看到什么、还有什么没验证。带着诚实缺口的局部报告，
  比一个满是窟窿的自信总结更有价值。

### PR 规模

- 目标大致 200–400 行改动。
- 超过 500 行就拆 PR，或者在评审者开始读之前先带他走一遍。
- 理由很实际：小 PR 评审快、冲突少、发现错了也容易回退。大 PR 往往被「信了」就批准，那
  恰好是评审的反面。

## 文档同步工作流

| 变更                             | 在同一个 PR 内更新                              |
| -------------------------------- | ----------------------------------------------- |
| 用户可见行为                     | README，**每一种**它使用的语言各一份            |
| 入口、数据流或模块边界           | 架构文档                                        |
| 配置项、其默认值或取值           | 配置参考                                        |
| 工具：名字、参数或返回文本       | 工具参考                                        |
| 触发器，或它的触发时机           | 触发器参考                                      |
| 用户可见文本                     | 每一份语言词典，成对改                          |
| 本规范中的任何内容               | 本文与它的译本，同章节                          |
| 任何变更                         | 变更日志里的一条 `[Unreleased]` 条目            |

- 具体是哪几个文件属于**配置**，不是本文的常量：`docs.readme`、`docs.changelog`、
  `docs.docsDir`、`docs.mirrors` 才是检查真正读的路径。没有 `docs/` 目录的项目只是少了
  几行要填；变更日志那一行处处适用。
- 成对文件要么一起动，要么都不动。半同步的一对比过期的那对更糟，因为它看起来有人维护。
- CI 强制的是可机械验证的部分：locale 键对齐，两份 SKILL 暴露相同章节、相同顺序。翻译
  读起来好不好，仍然是人工评审项。
- 文档描述 main 分支的当前状态。它不是版本化文档：要读旧版本的行为，checkout 对应的
  git tag。

### 文档同步不适用的情形

以下变更不需要改 README，也不需要改架构、配置、工具、触发器这几份文档：

- 纯内部重构，外部可见行为不变。
- 只改测试。
- 不改变用户可见行为的依赖升级。
- 代码风格或格式。
- CI 配置。

这个豁免只管「散文」。以上任何一项若确实改变了用户看到的东西，它照样需要变更日志
条目——两个义务是分开的，这份清单只豁免了其中一个。

## 版本发布（SemVer + Keep a Changelog）

- 版本号遵循 [SemVer](https://semver.org/lang/zh-CN/)：`MAJOR.MINOR.PATCH`。
  - `MAJOR`——不兼容变更。
  - `MINOR`——向后兼容的新增。
  - `PATCH`——向后兼容的修复。
- **0.x 阶段不做兼容承诺。** SemVer 允许 0.x 的 `MINOR` 位携带破坏性变更；本项目把这点
  明说出来，并在 CHANGELOG 里逐个标 `BREAKING`。
- `CHANGELOG.md` 遵循
  [Keep a Changelog 1.1.0](https://keepachangelog.com/zh-CN/1.1.0/)：`[Unreleased]` 段
  永远在最顶部，其下是六个分类 `Added`、`Changed`、`Deprecated`、`Removed`、`Fixed`、
  `Security`。
- 发版流程：
  1. 确认 `main` 是绿的，且所有预期变更都已合入。
  2. 把 `[Unreleased]` 的条目移到新的 `[<version>] - <YYYY-MM-DD>` 标题下，`[Unreleased]`
     原位保留、清空。
  3. 把 `package.json` 的 `version` 改成与新标题一致。
  4. 提交为 `chore(release): <version>`，然后打 tag `v<version>` 并推送。
  5. 从打了 tag 的提交执行 `npm publish` 发布。
  6. 验证发布真的落地：`npm view <package> versions` 显示新版本，或
     `npx <package>@latest --version` 装下来并报出新版本号。验证失败时，先查 dist-tag
     与 registry 状态，再假定发布成功了。
- 不要修改已发布的段落。更正写新条目。

### 预发布版本

- 预发布版本遵循 SemVer：`MAJOR.MINOR.PATCH-<pre-release>`。
- 常见标识是 `-rc.1`、`-beta.1`、`-alpha.1`，就绪程度依次递减。
- 预发布版本不推到 `latest`。用 `npm publish --tag next` 发布，免得有人误装候选版本。
- 示例：`0.2.0-rc.1`、`1.0.0-beta.3`。
- 候选版本与 `[Unreleased]` 不能同时宣称同一个变更。条目要么已移到 `-rc.1` 标题下，
  要么仍是未发布状态——选一个，并在候选版本在外期间保持它成立。跟进 `-rc.2` 时，往同一个
  版本标题里加，不要另开一个。

### 发版中断在半路

步骤是有序的，而一次发版可能死在任何两步之间。恢复时先弄清三件事实里哪件真的发生了，
而不是相信输出「说」走到第几步：

- **tag 建了，但什么都没发出去。** 修好原因，从同一个 tag 再发一次。一旦可能有人 fetch
  过这个 tag，就不要删掉重推；tag 是承诺，registry 条目是交付。
- **发布成功了，但验证仍显示旧版本。** 等。registry 传播要几分钟，而镜像或「发布年龄」
  策略可能让不带版本号的安装停在上一版一整天。结论之前先用一次 packument 读取确认——
  重复发布同一版本会失败，所以这个错误判断的代价是一个版本号。
- **发出去了，但是错的。** 什么都别改：打上 tag 的提交在实践中不可变。走「撤回已发布
  版本」，然后以后续 patch 落地修复。
- **发版提交本身错了**（漏了文件、日期错了）。若还没打 tag 也没发布，reset 重做；若 tag
  已存在，别动历史，向前更正。

### 发布说明

发布说明是一个版本的交付说明，发在「新版本出现时人们会看的地方」。它的读者是使用者与升级者，
不是写这次改动的开发者。它回答的是：**对我意味着什么、我要不要升级、怎么升。**

这些要写详细：

- **新增功能**：用户能感知到的变化，带一个简短的使用示例。
- **修复列表**：修掉了哪些用户看得见的缺陷。
- **破坏性变更**：必须显眼，附迁移步骤。
- **升级**：版本要求、配置变更，以及装之前或装之后必须做的事。
- **已知问题**：诚实列出。没有就写一行「无」，而不是删掉这一节——缺一节读起来像漏了。
- **致谢**（可选）：为这个版本做出贡献的人。

这些要简略或省略：

- 内部实现细节，以及重构的流水账。
- 一串 commit hash——用 changelog 的链接代替。
- 什么信息都没有的「杂项更新」。
- 每个 PR 的审查过程。

详略原则：用户视角详细（我能得到什么、我要改什么），内部视角简略（想看细节的给链接）。

条目取自该版本的 changelog 段落，逐字复制而不是重新概括：两边在事实上不一致时，以 changelog
为准，发布页是错的。升级、已知问题、致谢这三节是唯一不存在于 changelog 里的内容——changelog
记录的是「改了什么」，而这三节回答的是「改了什么」这个记录装不下的问题。

如果这个项目有不止一种语言的读者，就把两种语言放在同一页上，而不是二选一：

```markdown
[中文](#cn-v1.2.0) | [English](#en-v1.2.0)

<h3 id="cn-v1.2.0">v1.2.0</h3>

#### 新增

- 空配置自动回退到默认值，不必先写一份配置文件

#### 修复

- Windows 上配置里的 `C:\...` 被当成转义读不到

#### 破坏性变更

- 配置字段 `timeout` 更名为 `requestTimeout`；旧名仍兼容一个版本

#### 升级

`dsh plugin --profile <profile> add @melosic/dsh-dev-workflow@1.2.0`

#### 已知问题

- 无

<h3 id="en-v1.2.0">v1.2.0</h3>

#### Added

- An empty configuration now falls back to the defaults instead of requiring a file

#### Fixed

- A `C:\...` path in the configuration was read as an escape sequence on Windows

#### Breaking changes

- The `timeout` field is now `requestTimeout`; the old name still works for one version

#### Upgrade

`dsh plugin --profile <profile> add @melosic/dsh-dev-workflow@1.2.0`

#### Known issues

- None

Full Changelog: [v1.1.0...v1.2.0](https://.../compare/v1.1.0...v1.2.0)
```

第二种语言是同一批条目的译文，不是对它们的第二次概括。每种语言一个标题即可——每个下面用
`####` 再分小节可以，整页复制两遍不可以。代价是每次发版多一次翻译，换来一个不读 changelog
那种语言的读者也能用；如果项目确实只有一种读者，就不做，并且明确说明，而不是留半页空白。

### 废弃与移除

- 废弃某个东西：在 `[Unreleased]` 的 `Deprecated` 下加条目，说明替代方案与计划移除的时间。
- 废弃至少保留一个 `MINOR` 版本再移除。安全问题是可以跳过这个等待的唯一理由。
- 移除时写 `Removed` 条目；0.x 阶段还要标 `BREAKING`。

### 回滚

- 回滚一个已发布变更：用 `revert` 提交把它退回去，并在 `[Unreleased]` 对应分类下加条目，
  说明回滚了什么、为什么。
- 不要删掉原来的 CHANGELOG 条目。CHANGELOG 是「发生过什么」的记录，而那个版本确实发布过。
- 回滚是否需要单独发版，取决于原变更扩散了多远；用户已经开始依赖的东西被回滚，就需要。

### 撤回已发布版本

- 发布不足 72 小时的版本可以用 `npm unpublish` 移除。
- 超过 72 小时 `npm unpublish` 就不可用了。改用 `npm deprecate` 标记，然后发布一个修复
  版本。
- 废弃说明必须写清：问题是什么、影响哪些版本、应该用什么替代。读者是「已经装了坏版本」
  的人，这是他们唯一会看的地方。
- 永远不要靠删掉版本来掩盖一次坏发布。发一个新的。

## CHANGELOG 维护

CHANGELOG 只回答一个问题，给「正在决定要不要升级」的人：*对我而言变了什么？* 它不是
提交日志的摘要。

### 该写什么

- 任何用户可见的行为变更：新能力、修复、配置项变化、API 变化。
- 破坏性变更。必须写，带 `BREAKING` 标记与迁移说明。
- 安全修复——但在修复发布之前，条目里不要披露漏洞细节。
- 废弃：废弃了什么、替代方案是什么、计划何时移除。

### 不该写什么

- 内部重构、代码风格、测试改动、依赖升级。
- 提交信息的复述。CHANGELOG 不是提交日志。
- 实现细节，例如哪个函数改名了。
- 任何尚未发布的东西。
- 任何形式的敏感信息。

### 怎么写

- 用祈使句，直接对读者说。
- 一个变更一条条目。
- 写「对用户意味着什么」，不是「代码做了什么」。
- 破坏性变更要给出迁移路径。
- 一条条目一句话，最多 120 字，`ci:checks` 会量。发布说明是逐字从它抄过去的，
  条目长度就是发布页长度。
- 只写改动之后的样貌，不写改动之前的样子。「此前 X 是坏的，因为 Y，现在 Z」里的 X 和 Y
  属于提交信息和 PR 描述——将来排查的人会去那里看，读发布页的人只想知道现在是什么。
- 不加粗开头。`**标题。** 解释…` 是第二个标题，既占字数又和后面的句子重复。
- 要写三句以上，它要么是几件该拆开写的事，要么是在解释修复 *怎么* 做的。长到只能被
  跳读的 CHANGELOG 就是没人读的 CHANGELOG。

### 示例

| 坏条目                          | 差在哪                           | 更好的条目                                                          |
| ------------------------------- | -------------------------------- | ------------------------------------------------------------------- |
| `Fixed — fixed a bug`           | 读者看不出是否影响自己。         | `Fixed — a failed push left the branch dirty; the error now rolls back` |
| `Added — refactored the parser` | 重构既不是新增，也不是用户可见的。 | `Changed — the parser accepts a single leading "+" before a number`  |
| `Changed — updated dependencies`| 例行升级对用户不是变更。         | *（不写条目）*                                                       |

### 什么时候写

- 变更发生的那一刻，写进 `[Unreleased]` 对应分类。
- 不是发版时补。那时候细节已经丢了，条目会变得含糊。
- `docs`、`test`、`chore`、`ci`、`build` 类提交通常不需要条目。
- `feat`、`fix`、`perf` 需要。`refactor` 只有在改变了用户可观察的东西时才需要。`revert`
  需要。

### 并发编辑

`[Unreleased]` 是每条开着分支都会写的那一段，因此它也是本仓库最常见的冲突。三个习惯能让
冲突变小：

- 把条目加在分类的**顶部**，不是底部。最新的一条是读者最想先看到的，而「加到末尾」保证
  了和所有同样加了末尾的分支冲突。
- 解决 `CHANGELOG.md` 冲突时**两边都留**。CHANGELOG 的冲突从来不是选择题，两条条目都描述
  了发生过的事。
- 合并 `main` 之后，检查你的条目没有被重复，且分类标题仍是 Keep a Changelog 的顺序。

### 依赖升级

- 依赖升级本身不写 CHANGELOG 条目。
- 例外是改变了用户可见行为的升级——例如某个解析器现在拒绝它以前接受的输入。这种情况写在
  它真正所属的分类下，而不是 `Changed — dependencies`。

### 破坏性变更

- 写进 `[Unreleased]` 对应分类，并以 `**BREAKING:**` 开头。
- 给出迁移路径：应该改用什么，以及什么都不改会发生什么。
- 这在 0.x 阶段最重要，此时一次 `MINOR` 升级就可能携带该变更。

## 安全操作规范

破坏性 git 命令。它们会重写或丢弃历史，绝不能未经询问就跑：

| 命令                                     | 风险                                       |
| ---------------------------------------- | ------------------------------------------ |
| `git push --force` / `--force-with-lease`| 覆盖远端历史；可能丢弃提交                 |
| `git push --mirror`                      | 强制加删除：让远端完全变成你本地这样       |
| `git reset --hard`                       | 永久丢弃未提交的工作                       |
| `git clean -f`                           | 永久删除未跟踪文件                         |
| `git branch -D`                          | 删除提交可能只存在于本地的分支             |
| `git rebase`                             | 重写历史                                   |
| `git commit --amend`                     | 重写一个可能已经发布的提交                 |
| `git checkout -- .` / `git restore .`    | 丢弃全部未暂存的改动                       |
| `git checkout -f` / `git switch --discard-changes` | 强行切换，同样丢弃改动            |
| `git push --delete`                      | 删除别人可能正基于其工作的远端分支         |
| `--no-verify`                            | 跳过保护仓库的钩子                         |

`git restore --staged <path>` 不在这张表里：它把改动退回工作区，什么都没丢。不带 `--staged`
的 `git restore <path>` 是 `git checkout -- <path>` 的现代写法，它在表里。

- 这张表针对的是「别人也看得见的历史重写」。rebase 一条只有你、且从未推过的分支，什么都没
  重写。rebase 别人已基于其工作的分支——或 `main` 本身——才是这张表警告的情形，也是分支
  模型里要求用 `git merge main` 的原因。
- 绝不硬编码凭据，也绝不把凭据写进日志、夹具或文档。密钥来自环境变量或未跟踪的本地文件。
- 绝不以「检查一下」为由读取敏感文件：`.env`、`*.pem`、`*.key`、`id_rsa*`、`credentials`、
  `*.p12`、含 auth token 的 `.npmrc`，以及 `secrets/` 下的任何内容。
- 强推必须用 `--force-with-lease`，它会拒绝覆盖你尚未 fetch 的提交。这种写法只允许用在既
  不是 `main`、也不受保护的分支上；对 `main` 而言，任何形式的强推都不接受。裸 `--force`
  永远不是答案。
- 不要习惯性绕过 git 钩子。`--no-verify` 是应急出口，不是工作流。
- AI 助手不得在没有用户针对该具体动作的明确确认时执行破坏性操作，并且必须说明会丢什么。
- **别人能看见的每个动作同理。** push、打 tag、开 PR、发布，都以用户名义离开这台机器；
  在他们同意之前就说「done」，是这四件事共同的错误。把将离开的东西展示出来，等回答，然后
  才执行。强推两件事都占：还要额外展示将被覆盖的远端提交。
- 用户要求执行破坏性命令时，优先给可逆的写法，并说明为什么。
- 提交前扫描暂存 diff 里的凭据，用 gitleaks 这类密钥扫描器而不是肉眼。扫到就轮换密钥——
  只删提交不够。密钥一旦到过远端，就已经泄露了。

## 工具与守卫的边界

本插件是一组守卫与触发器，不是沙箱。分清它到哪儿为止，既能避免误信，也能省下「去配置一个
根本配不了的东西」的力气：

- **守卫看的是工具参数，不是运行中的进程。** 在脚本内部拼出来的路径，或经语言运行时读到的
  路径，`fileGuard` 都看不见——它匹配的是工具被调用时的那些词。
- **shell 解析是词法级的，不是 shell。** 守卫会读常见的藏匿处——命令替换、反引号、
  `sh -c` 的参数都会被当作命令行再解析一遍——但解释器是不透明的：`node -e "…"` 或
  `python -c "…"` 里面的内容没有任何检查会读。守卫拦的是破坏性命令的常见形态，也就是人
  真正会犯错的地方；它不是用来对抗刻意混淆的。
- **各守卫「可配置到什么程度」并不相同。** `gitGuard` 每条规则一个策略（强推、hard reset、
  rebase、amend、删分支、clean、丢弃工作区、`--no-verify`），`outwardGuard` 每个对外动作一个
  策略（push、tag、PR、发布）。`commandGuard` 只有一个策略覆盖所有已识别形态，因为它们共享
  唯一重要的性质——都不可撤销。`fileGuard` 与 `secretGuard` 是固定的 `deny`，没有逐条例外，
  唯一的放宽方式是整关；只在一个「暴露了也无所谓」的沙箱里这么做。
- **触发器检查的是动作，不是结果。** 提交信息在提交发生前检查；变更的文件在写入前检查。
  有些值要到命令执行时才确定，此时检查会明说不判定，而不是猜一个。
- **真正的边界是宿主。** 沙箱与审批策略决定工具能做什么。这些守卫存在的意义是让常见错误
  早点被发现——把一次绿色的运行理解为「没有明显问题」，绝不等于「安全已被证明」。
- **守卫抛错 = 这次调用报错，不会放行。** 宿主包住了整条 pre-execute 链路，守卫里抛出的异常
  会变成这次工具调用的错误。没有任何路径会把崩溃变成静默的放行——这是刻意的：被吞掉的异常
  等于守卫悄悄让开。
- **在子代理里，`ask` 等于拒绝。** 子代理没有自己的审批面，问不到人的问题按 `deny` 结算，
  而不是默认放行。守卫在子代理里照常生效，但设成 `ask` 的策略会拦住它们，不是只提醒。
- **哪些仓库被检查是配置，不是机器的属性。** DSH 按 profile 启用插件，而 profile 是按机器的
  ——但这套规则属于仓库。设成 `scope: 'marked'` 时，只有项目根目录带 `.dsh/dev-workflow.yml`
  的仓库才被检查；其余仓库里技能目录行不出现、所有守卫都让开，既不占常驻 token 也不打扰。
  默认是 `all`，与以前一样检查每个工作目录。如果某个仓库没有标记而你不确定规则适不适用，
  先问，不要假定适用——守卫的沉默不是认可。要启用某个仓库就敲 `/dev-workflow mark`
  （`unmark` 撤销），不必手建路径。

## 自动触发时机

- **提交之前**——按 Conventional Commits 检查提交信息，检查 `CHANGELOG.md` 是否需要
  `[Unreleased]` 条目，以及变更的文件有没有把对应文档一起带上。
- **开 PR 之前**——用提交信息规则检查标题（在 squash merge 下它就是落在 main 分支上的
  提交），并按模板的段落检查描述——默认是 `What` / `Why` / `How to verify` /
  `Type of change` / `Non-goals` / `Risk and rollback` / `Checklist`，除非
  `prSections` 另有说明。
- **发版之前**——检查版本号、tag 与 `package.json` 是否一致，以及 CHANGELOG 是否包含该
  版本。
- **没有触发器监听建分支动作。** 分支命名是本文要求的约定，不是插件强制执行的东西，
  所以命名不规范的分支不会被拦。
- **其余时候保持安静。** 不要主动把规范倒出来，不要读它的全文，不要打断无关工作。常驻成本
  保持在一条摘要。
- 用户无视某个提示时，让动作继续。不要重复它：**同一会话里、同一个问题的同一个提示只提
  一次——而且只在问题确实被摆到用户面前之后。** 拒绝不会被记住，所以同一条命令下次仍会被
  重新判定。重复的警告是噪音，而噪音会训练人闭眼点过。
- 每条提示都必须可操作：说清问题、给出期望的形式、提供一个具体修法。「提交信息无效」不是
  提示；「subject 有 63 个字符——Conventional Commits 建议不超过 50」才是。
