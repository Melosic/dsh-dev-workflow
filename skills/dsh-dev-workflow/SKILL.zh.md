# dsh-dev-workflow

本文件是本项目开发方式的单一事实源。它按需读取——以下任何内容都不占用常驻上下文。

## 核心原则

- **自动化优于自觉。** 工具能检查的规则就交给工具检查，不要指望人记得。凡可机械校验的项，
  都应落进 CI 或钩子。
- **原子化变更（推荐，非强制）。** 一个提交只解决一个独立逻辑问题；但原子性需要语义判断，
  因此它永远不是硬性门禁。
- **文档即代码。** 描述某项变更的文档，与该变更在同一个 PR 中一起交付。
- **质量门禁前置。** 类型检查、lint、格式与测试在评审之前跑完，让评审者读到的是意图而不是噪声。
- **安全默认，显式确认。** 破坏性操作默认「询问」，绝不默认「允许」。
- **按动作自动触发，不靠手动切档。** 工作流在用户即将提交、开分支或发布时出现。
  用户会忘记切档，但动作不会说谎。
- **平时安静。** 不唠叨、不每轮倾倒完整规范。常驻成本只有一行摘要，全文只在需要时读取。

## 分支模型（GitHub Flow）

- `main` 永远可发布，且受保护：禁止直接推送，一切变更通过 PR 合入，且必须通过必需检查。
- 工作发生在从最新 `main` 切出的短生命周期分支上：

  | 前缀        | 用途                |
  | ----------- | ------------------- |
  | `feature/*` | 新功能              |
  | `fix/*`     | 缺陷修复            |
  | `docs/*`    | 仅文档              |
  | `hotfix/*`  | 针对 `main` 的紧急修复 |

- 分支名全部小写、kebab-case（与提交信息里的 type 和 scope 风格一致）。名字必须能自解释：
  `feature/skill-md`、`fix/guard-force-push`——而不是 `feature/stuff` 或 `feature/NewStuff`。
- 一个分支只做一件事。
- 保持分支最新用 `git merge main`，**不要**用 `git rebase main`。在 squash merge 的工作流下，
  rebase 会重写分支自身的历史，评审者将看不到上次评审之后到底改了什么。
- 冲突在分支上解决，绝不在 `main` 上解决。
- 冲突解决之后，必须重新跑一遍 `pnpm typecheck`、`pnpm lint`、`pnpm test` 再提交。
  冲突解决可能改变代码语义，之前那次全绿不再覆盖它——不重新验证就提交，
  等于把冲突解决当成了无风险的文本合并。
- 合并使用 **squash merge**，这样 `main` 保持每个 PR 一个提交，历史线性。
- 落到 `main` 上的那个 squash 提交，信息取自 **PR 标题**，因此 PR 标题本身必须符合
  Conventional Commits。
- 分支上的各个提交会被压掉，不会出现在 `main` 的历史里。这就是 PR 标题比分支上
  任何单个提交都更重要的原因。
- PR 合并后立即删除分支。

### 分支保护

`main` 的保护写在仓库设置里，而不是靠约定。规则为：

- 禁止直接推送。
- 禁止 force push。
- 禁止删除。
- 必须走 PR，且至少一人 review。
- 所有必需的 CI 检查必须通过。
- 合并前分支必须与 `main` 保持最新。
- 所有评审对话都必须已解决。

这些规则配置在 GitHub 仓库上，因此对所有人一视同仁，包括管理员。

### hotfix 流程

- `hotfix/*` 分支从 `main` 切出，绝不从 feature 分支切出。
- 修好之后直接合回 `main`。本模型里没有 `develop` 或 `release` 分支可绕。
- hotfix 的 `CHANGELOG.md` 条目写入 `[Unreleased]`，和其他改动一样随下一次发布发布。
- 如果问题严重到必须立刻发布，走《撤回已发布的版本》那条流程，
  不要临时发明第二套流程。

## 提交信息规范（Conventional Commits）

```text
<type>(<scope>): <subject>

<body>

<footer>
```

- `scope` 可选；当变更范围明确时建议填写。
- **主题行**：祈使语气（用 "add"，不用 "added"），结尾不加句号，且不超过 50 字符。
  subject 用英文，以与 type 和 scope 保持一致——后两者本身就是英文。
- **正文**：每行不超过 72 字符，说明*为什么*。不要复述 diff 已经显示的内容。
  正文与页脚可以用英文或中文，但同一个项目内应选定一种并保持一致。
- **页脚**：引用 issue（`Closes #12`），并记录破坏性变更。

  | 类型       | 含义                                     |
  | ---------- | ---------------------------------------- |
  | `feat`     | 新增用户可见的能力                       |
  | `fix`      | 缺陷修复                                 |
  | `docs`     | 仅文档                                   |
  | `style`    | 格式调整，不改变行为                     |
  | `refactor` | 既非修复也非新功能的内部改动             |
  | `perf`     | 提升性能的改动                           |
  | `test`     | 新增或修复测试                           |
  | `build`    | 构建系统或依赖                           |
  | `ci`       | CI 配置与脚本                            |
  | `chore`    | 其他无处归类的维护工作                   |
  | `revert`   | 回退此前的提交                           |

- 破坏性变更：在类型或 scope 后加 `!`（如 `feat(api)!: ...`），**并**在
  `BREAKING CHANGE:` 页脚中说明。
- 页脚必须严格写作 `BREAKING CHANGE: <说明>`——全大写，冒号后一个空格。
  带连字符的 `BREAKING-CHANGE` 是另一个标记，不会被识别。
- 50/72 规则不是形式主义。许多工具会截断主题行，而按宽度折行的正文在终端与 diff 中都更易读。

### Issue 引用

- `Closes #12`——这个提交合入后，issue #12 可以关闭。
- `Refs #12`——这个提交与 issue #12 相关，但不关闭它。
- 多个 issue：`Closes #12, #15`。
- 只写 issue 号，不写完整 URL——仓库是已知的，而 URL 比它承载的信息更长。

## 原子提交（推荐实践）

- 一个原子提交恰好解决一个独立的逻辑问题，且能用一行意图描述清楚。
- 这是**推荐，不是要求**。原子性依赖语义判断——两处改动是否属于同一件事取决于意图，
  而非文件路径——因此它无法机械校验，也永远不是合并的门禁。
- 准备提交时，如果暂存的改动回答了不止一个问题，或回退该改动不得不分片进行，就拆分它；
  否则保持完整。
- **用户有最终决定权。** 若用户要求合成一个提交，就给出一个提交，并把取舍说明一次。
- pre-commit 触发器不检查原子性。它只检查可机械校验的项：提交信息格式、CHANGELOG、文档同步。

## PR 流程与质量门禁

提交前自查：

- [ ] 本地 `pnpm typecheck`、`pnpm lint`、`pnpm format:check`、`pnpm test` 全部通过。
- [ ] 暂存的改动只回答一个问题（见《原子提交》）。
- [ ] 提交信息符合 Conventional Commits。
- [ ] 受本次变更影响的文档已在同一提交或同一 PR 中更新。
- [ ] `CHANGELOG.md` 的 `[Unreleased]` 段已有对应条目。

PR 描述模板：

```markdown
## What

## Why

## How to verify
```

只有 CI 全绿、分支与 `main` 同步、且所有评审对话均已解决时，PR 才可合并。
绝不通过绕过失败的检查来合并：修掉根因，或如实报告阻塞点。

CI 失败时：

- 修根因。绝不通过改 CI 配置来绕过失败。
- 绝不使用 `--no-verify` 或等价手段跳过门禁。
- 如果确实是 CI 本身有 bug，为它单独提 issue，不要在无关的 PR 里临时改配置。

### 本地验证与 CI 的关系

- 上面那份本地自查清单是建议，不是硬性要求。
- CI 是硬门禁，不可绕过。
- 本地验证通过不等于 CI 一定通过——环境存在差异。
- 本地跑不过就别提交。
- 提交后 CI 失败，修根因，不要通过削弱检查来让它变绿。

### PR 粒度

- 改动行数控制在 200–400 行左右。
- 超过 500 行就该拆分，或提前给评审者做一次走查。
- 理由很实际：小 PR 评审快、冲突少、发现不对时也容易回滚。
  大 PR 往往只能靠信任放行，而这恰恰与评审的目的相反。

## 文档同步工作流

| 变更类型                       | 需在同一 PR 中更新                              |
| ------------------------------ | ----------------------------------------------- |
| 用户可见行为                   | `README.md` **与** `README.zh.md`               |
| 入口、数据流或模块边界         | `docs/ARCHITECTURE.md`                          |
| 配置项、其默认值或取值范围     | `docs/CONFIGURATION.md`                         |
| 工具的名称、参数或返回文本     | `docs/TOOLS.md`                                 |
| 触发器或触发时机               | `docs/TRIGGERS.md`                              |
| 用户可见字符串                 | `locale/en.json` **与** `locale/zh.json`        |
| 本规范中的任何内容             | `SKILL.md` **与** `SKILL.zh.md`，章节一致        |
| 任何变更                       | `CHANGELOG.md` 的 `[Unreleased]` 条目           |

- 成对的文件要么一起改，要么都不改。半同步的一对比过期的一对更糟，因为它看起来是被维护着的。
- CI 只强制可机械校验的部分：locale 字典 key 对齐，以及两份 skill 文件暴露的章节数量与顺序一致。
  译文读起来好不好，仍然属于人工评审项。
- `docs/` 始终描述 `main` 的当前状态。它不是带版本号的文档：要了解某个旧版本的行为，
  请检出对应的 git tag。

### 不需要文档同步的情况

以下变更无需更新 `README.md` 或 `docs/`：

- 纯内部重构，外部可见行为不变。
- 纯测试变更。
- 依赖升级，且不影响用户可见行为。
- 代码风格调整、格式化。
- CI 配置调整。

这项豁免只覆盖叙述性文档。如果上述任一变更确实改变了用户看到的东西，
它**仍然**需要 CHANGELOG 条目——两项义务是分开的，这里只免除了其中一项。

## 版本发布（SemVer + Keep a Changelog）

- 版本号遵循 [SemVer](https://semver.org/lang/zh-CN/)：`MAJOR.MINOR.PATCH`。
  - `MAJOR`——不兼容的变更。
  - `MINOR`——向后兼容的新增。
  - `PATCH`——向后兼容的修复。
- **项目处于 0.x 阶段时不做任何兼容性承诺。** SemVer 允许 0.x 的 `MINOR` 位变更携带破坏性变更；
  本项目把这一点写明，并在更新日志中为每个破坏性变更标注 `BREAKING`。
- `CHANGELOG.md` 遵循
  [Keep a Changelog 1.1.0](https://keepachangelog.com/zh-CN/1.1.0/)：`[Unreleased]` 段常驻顶部，
  其下是六个分类 `Added`、`Changed`、`Deprecated`、`Removed`、`Fixed`、`Security`。
- 发布流程：
  1. 确认 `main` 全绿，且所有预期变更已合入。
  2. 把 `[Unreleased]` 下的条目移到新的 `[<版本号>] - <YYYY-MM-DD>` 标题下，
     并把 `[Unreleased]` 留在原处、清空。
  3. 把 `package.json` 的 `version` 提升到与新标题一致。
  4. 以 `chore(release): <版本号>` 提交，然后打标签 `v<版本号>` 并推送。
  5. 从该标签对应的提交执行 `npm publish`。
  6. 验证发布确实成功：`npm view <包名> versions` 应能看到新版本，
     或 `npx <包名>@latest --version` 应能装上并报出版本号。验证失败时，
     先检查 dist-tag 与 registry 状态，再假设发布成功了。
- 不要修改已发布的小节。更正应作为新条目写入。

### 预发布版本

- 预发布版本遵循 SemVer：`MAJOR.MINOR.PATCH-<pre-release>`。
- 常见标识为 `-rc.1`、`-beta.1`、`-alpha.1`，其就绪程度依次递减。
- 预发布版本不推送到 `latest` tag，用 `npm publish --tag next` 发布，
  以免有人误装到候选版本。
- 示例：`0.2.0-rc.1`、`1.0.0-beta.3`。

### 废弃与移除

- 废弃一个功能时，在 `[Unreleased]` 的 `Deprecated` 分类下写条目，
  说明替代方案与计划移除的时间。
- 除非是安全原因，废弃后至少保留一个 `MINOR` 版本再移除。
- 移除时写入 `Removed` 分类；在 0.x 阶段同时标注 `BREAKING`。

### 回滚

- 回滚一个已发布的变更时，用 `revert` 类型提交，并在 `[Unreleased]` 的对应分类下
  写明回滚了什么、为什么。
- 不要在 CHANGELOG 中删除原条目。更新日志记录的是已发生的事实，
  而一个已经发布的版本确实发生过。
- 回滚后是否需要新版本发布，取决于原变更扩散的范围；如果用户已经依赖上它，就需要。

### 撤回已发布的版本

- 发布不足 72 小时的版本可以用 `npm unpublish` 移除。
- 超过 72 小时后 `npm unpublish` 不再可用，改用 `npm deprecate` 标记问题版本，
  然后发布修复版本。
- deprecate 的说明必须写明问题、受影响的版本、以及该用什么替代。
  读到它的人已经装上了出问题的版本，那是他们唯一会看到它的地方。
- 绝不用删除版本的方式掩盖一次糟糕的发布。发一个新版本。

## CHANGELOG 维护

更新日志回答的是升级者最关心的一个问题：*对我而言变了什么？* 它不是提交日志的汇总。

### 该写什么

- 任何用户可见的行为变化：新增能力、修复、配置项变化、API 变化。
- 破坏性变更。必须写，标注 `BREAKING` 并附迁移说明。
- 安全修复——但在修复发布之前，条目中不要披露漏洞细节。
- 废弃：什么被废弃、替代方案是什么、计划何时移除。

### 不该写什么

- 内部重构、代码风格调整、测试变更、依赖升级。
- 提交信息的复述。CHANGELOG 不是 commit log 的汇总。
- 实现细节，例如某个函数被改了名。
- 尚未发布的功能。
- 任何敏感信息。

### 怎么写

- 用祈使句，面向用户。
- 一条一个变更。
- 说清楚对用户的影响，而不是代码做了什么。
- 破坏性变更要写迁移路径。

### 示例

| 差条目                            | 差在哪                                | 好条目                                                              |
| --------------------------------- | ------------------------------------- | ------------------------------------------------------------------- |
| `Fixed — 修复了一个 bug`          | 读者无从判断这是否影响自己。          | `Fixed — 推送失败会留下脏分支；现在出错时自动回滚`                  |
| `Added — 重构了解析器`            | 重构既不是新增，也不是用户可见的。    | `Changed — 解析器现在接受数字前的一个前导 "+"`                      |
| `Changed — 更新了依赖`            | 例行升级对用户而言不是变更。          | *（不写条目）*                                                       |

### 什么时候写

- 每次用户可见变更发生时，就写入 `[Unreleased]` 的对应分类。
- 不是发布时才补。到那时细节已经丢失，条目会变得含糊。
- `docs`、`test`、`chore`、`ci`、`build` 类型的提交通常不需要条目。
- `feat`、`fix`、`perf` 需要。`refactor` 仅在用户可观察到变化时需要。`revert` 需要。

### 依赖升级

- 依赖升级本身不写 CHANGELOG。
- 例外是引入了用户可见行为变化的升级——例如某个解析器现在拒绝以前接受的输入。
  这种要按它实际所属的变化类型写入对应分类，而不是写成 `Changed — 依赖`。

### 破坏性变更

- 在 `[Unreleased]` 对应分类下写条目，条目前加 `**BREAKING:**`。
- 附迁移说明：该用什么替代，以及不迁移会发生什么。
- 在 0.x 阶段这一点尤其重要，因为 `MINOR` 位变更就可能携带破坏性变更。

## 安全操作规范

危险 git 命令。它们会重写或丢弃历史，绝不可未经提示就执行：

| 命令                | 风险                                     |
| ------------------- | ---------------------------------------- |
| `git push --force`  | 覆盖远端历史；可能丢弃他人的提交         |
| `git reset --hard`  | 永久丢弃未提交的工作                     |
| `git clean -f`      | 永久删除未跟踪的文件                     |
| `git branch -D`     | 删除分支，其提交可能不存在于其他任何地方 |
| `git rebase`        | 重写历史                                 |
| `git commit --amend`| 重写可能已发布的提交                     |
| `git checkout -- .` | 丢弃所有未暂存的改动                     |
| `--no-verify`       | 跳过保护本仓库的钩子                     |
| `git push --delete` | 删除他人可能作为基础的远端分支           |

- 绝不硬编码凭据，也绝不把凭据写进日志、测试夹具或文档。密钥来自环境变量或未纳入版本控制的本地文件。
- 绝不为了「检查一下」而读取敏感文件：`.env`、`*.pem`、`*.key`、`id_rsa*`、`credentials`、
  `*.p12`、含 auth token 的 `.npmrc`，以及 `secrets/` 下的任何内容。
- 强制推送必须使用 `--force-with-lease`，它会拒绝覆盖你尚未获取的提交。裸 `--force` 绝不是答案。
- 不要把绕过 git 钩子当成习惯。`--no-verify` 是紧急情况的逃生通道，不是工作流。
- AI 助手不得在未获得用户对*该具体操作*的显式确认前执行破坏性操作，且必须说明会损失什么。
- 当收到破坏性命令的请求时，优先采用可回退的形式，并说明理由。
- 提交前应扫描暂存的改动是否包含密钥模式。一旦发现，立即轮换密钥——只删掉提交是不够的。
  已经推到远端的密钥视为已泄露。

## 自动触发时机

- **提交前**——检查提交信息是否符合 Conventional Commits、`CHANGELOG.md` 是否需要
  `[Unreleased]` 条目，以及被改动的文件是否带上了它们的文档。
- **开分支、创建 PR 或发布前**——检查分支命名、提交前自查清单与发布步骤。
- **其余时间保持安静。** 不要主动推销规范，不要读取全文，不要打断无关工作。
  常驻成本始终只保持一行摘要。
- 如果用户忽略了提示，就让操作继续，不要重复提示：**同一会话中针对同一问题的同一提示只提一次。**
  重复的警告是噪声，而噪声会训练人无脑点过警告。
- 每条提示都必须可操作：指出问题、给出期望形式、并给出具体修法。
  「提交信息无效」不是提示；「主题行 63 字符——Conventional Commits 建议不超过 50」才是。
