# 国际化

本文件说明本插件的文本从哪来、按什么规则选语言，以及为什么审批提示要走一条特别的路。

规则一句话：**用户可见的字符串一律走 `t()`，不得硬编码。** 这条由 `AGENTS.md` 规定，
也是 code review 的检查项之一。

## 语言与字典

`src/i18n.ts` 定义了两个语言，以及它们的字典文件：

| Locale | 字典 |
| --- | --- |
| `en-US` | `locale/en.json` |
| `zh-CN` | `locale/zh.json` |

字典是**扁平的 JSON**，key 用点分路径、值是模板字符串：

```json
{
  "tool.check_commit_message.error.empty": "The commit message is empty. …"
}
```

读取方式是 `createRequire(import.meta.url)` 加 `require('../locale/en.json')`——字典是数据，
不是模块图里的边；编译产物在 `lib/`，字典在 `locale/`，两者相对位置固定。每个语言只读一次，
之后缓存在 `Map<Locale, Record<string, string>>` 里。

插值形如 `{name}`，由 `createTranslator()` 用 `/\{(\w+)\}/g` 替换。**缺失的 key 回退为 key 本身**
（`messages[key] ?? key`），所以漏翻译会以 `tool.foo.bar` 这种形式显眼地出现在输出里，
而不是静默打印 `undefined`。

## 语言怎么选

配置项 `locale` 有三个取值：

| 取值 | 行为 |
| --- | --- |
| `'auto'`（默认） | 读 `Intl.DateTimeFormat().resolvedOptions().locale`，以 `zh` 开头则 `zh-CN`，否则 `en-US` |
| `'en-US'` | 固定英文 |
| `'zh-CN'` | 固定中文 |

`auto` 在**每次需要文案时解析**（`src/index.ts` 的 `refreshLocale()`，由 `t()` 与 `runtime.locale()`
调用），解析结果只在**值真的变了**时才重建字典。所以整个生命周期里通常只有一种语言，
但改配置后不必重启：设置面板写入 `locale` 后，宿主把新值提交进运行中的配置，插件收到
`loader/volatile-update` 就重新解析一次（`resync()`），技能正文与提示语随之切换。
这样技能目录条目与技能正文永远是同一种语言——两者走同一个 `refreshLocale()`。
`/dev-workflow status` 会同时显示解析结果和配置里的原始值（`Locale: en-US (configuration says "auto")`），
避免「我明明配了中文」这类误解。设置面板在选中 `auto` 时也标出解析结果
（`hint.localeResolved`：`「自动」跟随本机语言，当前为：中文（zh-Hans-HK）。`）——
那是浏览器侧用同一条 `zh` 前缀规则的复刻，不是宿主回传的值。

用 `Intl` 而不是读环境变量，是为了不手工解析 `LANG` / `LC_ALL` / Windows 的
`UserDefaultUILanguage`——平台差异交给运行时。

## 字典目录为什么是 `locale/`

DSH 约定是**单数 `locale/` 加短语言 id**：`locale/en.json`、`locale/zh.json`。
宿主读插件展示元数据时拼的路径就是 `${specifier}/locale/en.json`。

曾经用过 `locales/` 加 `en-US.json` / `zh-CN.json`，是非约定写法，已修正（见 CHANGELOG 的
`Changed` 段）。注意**插件内部的 `Locale` 类型仍写作 `en-US` / `zh-CN`**，这只是内部标识，
与文件名无关。

## 审批提示为什么给两份

`tools/pre-execute` 返回 `ask` 时，DSH 通过审批服务向客户端提问。这份提示的**显示语言由
客户端决定**，与本插件的 `config.locale` 无关——两者可能不同。因此 `displayReason` 同时给出
两份文本：

```ts
displayReason: {
  en: explain(hit, createTranslator('en-US')),
  zh: explain(hit, createTranslator('zh-CN')),
}
```

**中文的键必须是字面 `zh`。** 客户端把 locale 小写化后按 `zh` / `en` 匹配，并以 `en` 兜底；
写 `zh-CN` 永远匹配不上，会静默退回英文。

### 问题清单也必须就地重跑

这一点踩过坑。第一版只翻译了提示的外层包装，里面的问题清单还是按插件 locale 渲染的，
结果英文提示里嵌着中文条目——等于没翻。

正确做法是**用对应语言的翻译器把整次判定重新跑一遍**。`src/checks.ts` 的 `evaluate()` 之所以
是纯函数（输入是提交信息与文件列表，输出是字符串数组），就是为了这个：

```ts
displayReason: {
  en: english('trigger.pre_commit.ask', {
    details: detailsOf(evaluate(input, config, english), english),
  }),
  zh: chinese('trigger.pre_commit.ask', {
    details: detailsOf(evaluate(input, config, chinese), chinese),
  }),
}
```

同理，`src/guard/git-guard.ts` 的守卫理由是字典 key（`security.guard.force_push`），
渲染时才用对应语言的翻译器展开。四道守卫都走这一条：`GuardHit.reason` 与
`GuardHit.suggestion` 是 key，`GuardHit.params` 只放需要插值的东西——而 secret-guard 往里
放的**只有模式名**（`AWS access key` 这类语言中立的技术名），它匹配到的那个值是唯一
绝不进入任何输出、也不进入审计记录的东西。

## 同步规则

`locale/en.json` 与 `locale/zh.json` 的 **key 集合必须完全一致**，由 CI 强制：

```bash
pnpm ci:checks
# locale keys aligned (86 keys); bundle patch declared and shipped; skill headings aligned (28 sections); published entry points present (4 checked).
```

（括号里的数字是脚本按实际内容算出的当前值，不要照抄去断言 CI。)

`scripts/ci-checks.mjs` 把两份字典的 key 拉平后双向比对，任一侧多出或缺少 key 都会失败。
所以新增文案必须两个文件一起改，这是 PR 里最常见的一类 CI 失败。

**CI 只校验 key 对齐，翻译正确性是人工审查项。** 机器能发现「漏了一条」，
不能发现「这条中文看着像机翻」。改文案时请把两种语言都当作正式文本对待。

同样的成对规则也适用于文档与技能：

| 改了 | 必须同步 |
| --- | --- |
| `README.md` | `README.zh.md` |
| `locale/en.json` | `locale/zh.json` |
| `skills/dsh-dev-workflow/SKILL.md` | `skills/dsh-dev-workflow/SKILL.zh.md`（章节数量与层级顺序一致） |

前两对也写在配置的 `docs.mirrors` 里，因此尝试只改一半时，插件自己的 `check_doc_sync`
会在提交前把这件事指出来——CI 与插件检查同一份约定。

## 什么样的文本走 `t()`

| 类型 | 是否走 `t()` | 例子 |
| --- | --- | --- |
| 用户可见的输出、提示、错误 | 是 | 工具输出的问题清单、审批提示、`/dev-workflow status` |
| 工具与参数的描述（模型可见） | 是 | `tool.check_commit_message.description` |
| 技能目录条目的摘要 | 是 | `skill.summary` |
| 面向贡献者的长文档 | 否 | `docs/`、`README`、`CONTRIBUTING.md` |
| 代码注释 | 否（且必须用英文） | `// The guard is a separate listener…` |
| 诊断日志 | 否 | `[dsh-dev-workflow] git guard: security.guard.force_push` |

最后两行的理由：注释与日志是给维护者看的，双语维护成本远大于收益；而**长文档单语、
面向用户的短文本双语**是本仓库的既定取向（`AGENTS.md` 的「面向用户的短文本双语，
面向贡献者的长文档单语」）。

诊断日志里出现的是字典 key 而不是译文，这是有意的：日志用于定位「哪个规则触发了」，
key 是稳定的标识符，不受语言影响。

## 相关工作

- 字典文件：`locale/en.json`、`locale/zh.json`
- 解析与翻译实现：`src/i18n.ts`
- 双语审批提示的实现：`src/triggers/shared.ts`（`askAbout()` 同时构造 `en` 与 `zh` 两份
  `displayReason`，三个触发器共用）、`src/guard/shared.ts`（`decide()` 同理）、
  `src/guard/git-guard.ts`
- 审批策略为 `never` 时的拒绝说明：`src/approval-policy.ts`（`unaskable()` 追加
  `approval.disabled` 键，七个监听器共用）
- CI 守护：`scripts/ci-checks.mjs`
- 贡献者规范：`CONTRIBUTING.md`
