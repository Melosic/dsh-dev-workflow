# 002 — 做成插件，而不是模式或预设

## 状态

已接受（2026-10）

## 背景

DSH 里一个功能可以以几种形态落地，落地形态决定了它对用户意味着什么、和谁冲突、
以及怎么安装：

1. **插件（plugin）**——通过 `cordis.patch.yml` 追加到 profile 的 Cordis 入口列表。
   和用户已有的其它插件同时存在，互不知道对方。
2. **模式（mode）**——改变 agent 的工作方式，例如 `@deepseek-ai/dsh-plan-mode` 的 `/plan`：
   进入后 agent 先探索设计、产出计划，再由用户审阅后才执行。
3. **预设（preset）**——`@deepseek-ai/dsh-agent-preset-registry` 里的组合。按该包的说明，
   预设**决定模型看到的工具 schema 与提示词片段**，每个 agent 挂载一个预设 revision，
   一次会话跑在哪个预设上会写进会话日志。

本仓库的规范要求（`AGENTS.md`、以及贯穿五个阶段的「插件而非模式」）是：
**不碰 DSH 内置的模式，在用户已有的模式之上提供工作流能力。**

工作流守门员要做的事——在提交前插一句话、提供两个检查工具、拦一下危险 git 命令——
与「改变 agent 的工作方式」不是一回事。

## 决定

**本插件始终是一个 plugin。** 它不注册模式、不注册预设、不改变 agent 的循环，
也不试图成为「第五种模式」。安装方式就是 `cordis.patch.yml` 往 profile 入口列表里追加一条：

```yaml
- insert:
    - id: dsh-dev-workflow
      name: '@melosic/dsh-dev-workflow'
```

它的能力通过三条**现有**的宿主机制提供：技能 provider、工具注册、事件监听。

## 后果

**好的后果**

- **与模式正交。** 用户今天用 plan 模式、明天用别的模式，插件照常工作——它不参与模式选择，
  也不要求用户为了用它而切换工作方式。这正是「按动作自动触发，不靠手动切档」的实现前提：
  开关是 `/dev-workflow on|off` 这个插件自己的动作，不是模式切换。
- **安装面小。** 一条 patch 记录。插件关掉（`mode: 'off'`）时它连注册都不做，
  等价于没装。
- **不抢别人的位置。** 预设决定工具 schema 与提示词片段，是一份会被争夺的资源；
  插件只追加自己的两个工具和一行技能目录条目，名字带前缀、不覆盖任何东西。
- **可以用同样的方式卸载。** 移除 bundle、重启 profile 即可，不残留模式状态。

**坏的后果**

- **插件看不见会话外的操作。** 模式可以规定 agent 怎么做，但用户在自己的终端里
  `git commit` / `git push --force` 时谁都拦不住。这个缺口由 husky 与 GitHub 分支保护补上，
  不是插件能修的——它是形态本身的边界（详见 [docs/SECURITY.md](../SECURITY.md)）。
- **表达力受限。** 插件不能说「在这个会话里，agent 必须先……才能……」。它能做的只是
  在工具执行的门禁上判断与放行，以及提供一个可以被忽略的技能。
- **用户需要自己选择打开它。** 模式往往是「一进会话就在」，插件需要装进 profile。
  这是可见性的代价，也是可撤销性的来源。

**中性后果**

- 插件的入口 ID 必须与 DSH 已有的 loader 条目不冲突（`dsh-dev-workflow`），
  由 `scripts/ci-checks.mjs` 校验 `cordis.patch.yml` 既被声明、又随包发布。
- 「模式」这个概念对本插件而言只剩 `mode: 'on' | 'off'` 这一个配置项，
  含义是「注册/不注册资源」，与 DSH 的模式无关。文档里必须说清这一点，否则会误导。

## 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 做成一个 DSH 模式 | 直接违反本仓库的第一条定位（「插件而非模式」）。模式改变 agent 的工作方式，而守门员要做的是「在用户已经决定提交的那一刻插一句话」——前者是全局的，后者是局部的 |
| 做成一个预设 | 预设决定工具 schema 与提示词片段，用户选预设就等于选了工具集。工作流规范应当对**所有**预设生效，而不是成为其中一个的专属内容；做成预设还意味着用户必须放弃原来的预设才能用它 |
| 做成 SKILL.md 就够，不要插件 | 技能可以被忽略，而且技能无法执行任何动作：不能拦 `git push --force`，不能读工作区跑文档同步检查。第一版就验证过——纯技能是「建议」，插件的价值在于少数几个必须发生的时刻 |
| 做成 husky 钩子 | husky 只在用户自己的终端上跑，看不见 agent 在会话里执行的 git 调用；而 agent 正是本插件的主要使用场景。反过来，会话外的场景插件也覆盖不了，两者是互补而非替代 |
| 做成 MCP server | MCP 提供的是工具，不是门禁。它不能拦截一个**已经在执行路径上**的工具调用，而这正是 git-guard 的全部意义 |
