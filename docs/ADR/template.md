# ADR 模板

复制本文件到 `docs/ADR/NNN-short-title.md`（`NNN` 是三位递增序号，标题用短横线分词），
然后替换每一节的内容。

**写一份 ADR 的门槛：这个决定之后会被问「为什么这样做」。** 也就是说，它必须满足至少一条：

- 有真实的取舍——被放弃的方案同样讲得通，未来有人可能想改回去；
- 从代码本身读不出理由——字段的默认值、某个 `ctx.get` 而不是 `inject`、某种分层方式；
- 一旦违反就会出问题，但违反时不会立刻报错。

不满足这些的就不要写。**ADR 不是变更日志**：改了什么由 CHANGELOG 记录，
ADR 只记录「为什么是这个而不是那个」。已经被推翻了决定也不要删除——
在后面加一条新 ADR 并把旧标记为 `已取代`，保留当初的推理过程。

## 状态

起草中 / 已接受 / 已取代（被 `NNN-...` 取代）/ 已废弃

## 背景

是什么情况迫使要做这个决定？写清楚约束：DSH 的实际行为、已有的代码契约、
验收标准、token 预算之类的硬边界。**事实要能核对**——引用文件路径与行号、
引用官方包里的实现，而不是「据说」「一般来说」。

## 决定

用一两句话说明决定本身，主动语态：「我们采用 X」。

## 后果

这个决定之后必须接受什么。

**好的后果**：它解决了什么、让什么事变简单或变便宜。

**坏的后果**：它放弃了什么、引入了什么新的负担或限制。这一节不许写「没有缺点」——
如果一个决定看起来没有代价，通常说明还没想清楚。

**中性后果**：因此产生的、之后需要遵守的约定（例如「新增文案必须同时改两份字典」）。

## 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 方案 A | 为什么它不如当前选择。要具体到可核对的事实 |

这一节是 ADR 最有价值的部分。没有它，未来的读者（包括几个月后的作者本人）
只能看到「我们这么做」，看不到「为什么不那么做」，于是会重新踩一遍已经踩过的坑。
