# 004 — 按动作自动触发，不让用户手动切档

## 状态

已接受（第七阶段）；本 ADR 记录的设计曾在更早的尝试中被否决过

## 背景

一套工作流规范要生效，先得回答「它什么时候生效」。有三个位置可以放这个答案：

1. **用户手动切档。** 用户觉得自己要干正事了，切到「严格模式」；干完了切回去。
2. **每轮自动生效。** 每条请求都带上规范全文、都跑一遍检查。
3. **按动作生效。** 平时什么都不做，只在特定动作发生的那一刻介入。

方案 2 的成本在 [003](003-summary-plus-on-demand.md) 里算过：2600 token/轮，高一个数量级。

方案 1 看起来是省钱的答案——只在该严格的时候严格。**它失败过，而且失败的方式与
实现的巧妙程度无关：用户会忘记切。** 忘记切的用户得到的不是「宽松一些的工作流」，
而是「一个以为装着、其实没在工作的守门员」——比没装更糟，因为他会在
`git push --force` 之后才发现没人拦。

这个教训还有一个更隐蔽的版本：档位越多，忘记得越彻底。三档意味着用户要记住
「我现在在哪一档」「这个任务该用哪一档」「切回来没有」三件事，而这三件事没有一件
会在他即将提交的那一刻提醒他。

与此同时，DSH 的事件模型已经提供了方案 3 所需要的全部位置。
`tools/pre-execute` 是一个 waterfall：`(exec, next) => Promise<PreToolDecision>`，
决定是 `allow` / `deny` / `ask` / `cancel`。触发时机由**动作**定义，而不是由用户的记忆定义。

## 决定

**插件按动作自动触发。** 没有一个「严格/标准/宽松」的档位让用户选择；
严格程度由动作本身决定，写在代码里。

- 提交前检查提交信息与文档同步（`tools/pre-execute` 读到 `git commit` 时）。
- 开 PR 前检查标题与描述（读到 `gh pr create` 时）；发版前检查版本与 CHANGELOG
  （读到 `git tag` / `npm publish` 时）。
- 破坏性动作按各自的档位处理：git 与命令守卫默认 `ask`（可重做的工作，问一次是合理的），
  file 与 secret 守卫固定 `deny`（凭据发出去就收不回）。

**配置项里只有一个 `mode: 'on' | 'off'`，它回答的不是「今天多严格」，而是「要不要装这个插件」。**
`on` 时注册资源、按动作介入；`off` 时什么都不注册，常驻成本为零。
这是一个安装开关，不是工作流档位——文档里必须说清这一点，否则会被当成方案 1 重新引入。

另外有一个 `enableOwnTrigger: boolean`（默认 `true`），语义是「仓库里是否已经用 husky /
commitlint 自己管这事了」。它是**对仓库现状的描述**，不是让用户临时放宽，且默认值站在
「要检查」那一侧。

## 后果

**好的后果**

- **正确性与用户的记性解耦。** 检查发生在动作发生的那一刻，不需要用户先想起什么。
  用户可以完全不知道本插件存在，而每次提交仍然被看过。
- **配置面只剩一个开关。** 没有「我到底在哪一档」的状态，也没有「这个任务是哪一档」的判断，
  也就没有切错的可能。默认值只能是 `on`，因为默认 `off` 等于默认不工作。
- **`off` 是干净的一个档。** 因为它实现成「注销注册」而不是「注册但静默应答」，
  关掉之后连工具定义都不在上下文里——这是 `mode: 'off'` 常驻增量为 0 的原因。
- **严格程度可以按动作区分。** `git commit` 的检查拿 `ask`（错过一次检查不致命），
  而把 `AWS_SECRET` 写进文件拿 `deny`（没有第二次机会）。这在只有一个用户档位的设计里
  是表达不出来的——要么全严、要么全松。

**坏的后果**

- **用户失去了临时放宽的能力。** 想「这次就让我直接提」只能改配置或关掉整个插件，
  颗粒度是插件级的，不是检查项级的。这是有意的取舍：细颗粒度的放宽就是方案 1，
  只是换了个入口名字。
- **介入时机必须被猜准。** 自动触发的正确性取决于「动作识别」的正确性。
  事件目录里没有 PR 创建或发版事件，所以这两处只能从 shell 命令行识别
  （见 [docs/TRIGGERS.md](../TRIGGERS.md)）；识别不到就不会介入，而且不会报错。
- **模型感知不到检查项的存在。** 用户没被提示过 `ask`，就不知道有这条规则；
  规范全文仍然需要模型自己去读。
- **`enableOwnTrigger: false` 是一扇可以被误开的门。** 用户填 `false` 之后就真的不再检查了。
  能做的只是把默认值放在安全侧、并在文档里写清它的语义是「我有别的工具做这件事」。

**中性后果**

- **同一会话同一问题只提示一次。** 提示被忽略后动作照常继续——自动触发不等于无限唠叨。
  这条规则由 `src/state.ts` 强制：key 是 `${sessionId}:${checkType}:${targetId}`，
  内存 per-session、重启重置、跨会话允许重新提示。
- 新增一个自动介入点，必须同时说明它的动作识别规则与它在识别不到时的行为。
- `/dev-workflow check` 保留了一条手动路径，但它是**补充**而不是主路径：
  它服务的是「我现在就想跑一遍」，不是「我先切个档」。

## 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 手动切档（严格 / 标准 / 宽松，或更多档） | 用户会忘记切。忘记切的后果是「以为在保护、其实没有」，比不装更糟。档位越多忘记得越彻底。根本问题不是档位够不够多，而是提示时机对不对 |
| 让用户进入一个「工作流模式」（像 plan 模式那样） | 违反本仓库的第一条定位（[002](002-plugin-not-preset.md)：插件而非模式）。而且它把「要不要守规矩」变成一个用户要主动进入的状态，与手动切档是同一个失败模式，只是入口更长 |
| 每轮都自动生效 | 常驻成本 2600 token/轮（[003](003-summary-plus-on-demand.md)），且会在用户没在提交时也说话——违反「平时安静」 |
| 只提供手动工具，不做任何自动介入 | 这就是任务书里的降级路径，只在「DSH 拦不住这个动作」时才使用。核对结论是三个断点都拦得住（都经过 `bash` / `pwsh`），所以不适用；即便适用，它也意味着回到「用户得记得跑」 |
| 把严格档位做成配置项（`strictness: 'loose' \| 'strict'`） | 配置项不会提醒用户它现在是哪一档，于是与手动切档一样会「忘记切」——区别只是忘在配置文件里而不是忘在 UI 里。而且它会立刻膨胀成「每个检查项一个档位」 |
| 默认 `off`，让用户主动开启 | 默认不工作等于默认没有守门员。默认 `on` 的理由是它只在关键节点说话，本身就不打扰（[003](003-summary-plus-on-demand.md) 的成本核算）：`on` 的代价是几百 token 常驻，`off` 的代价是守卫不存在 |
