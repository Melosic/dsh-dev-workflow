# 001 — 规范放在技能里，不放系统提示

## 状态

已接受（2026-10）

## 背景

这个插件要把一套开发工作流规范交给模型：分支命名、Conventional Commits、文档同步、
CHANGELOG 规则、危险操作清单。规范本身很长——`skills/dsh-dev-workflow/SKILL.md` 与
`SKILL.zh.md` 合计两万字符量级，当前体量见 [docs/TOKEN-BUDGET.md](../TOKEN-BUDGET.md)。

它必须在**需要的那一刻**已经可用：模型决定提交时，不应该还需要用户先提醒「记得读规范」。
同时它是**每一条请求**都要付的固定成本，因为插件挂载后就一直在那里。

DSH 提供两个投递位置：

1. **系统提示**（`ctx.systemPrompt` 一类的注入口）——每轮请求都会带上，内容是硬成本。
2. **技能**（`ctx.skills.registerProvider()`）——模型看到的是目录条目（`name: description`），
   正文经 `SkillProvider.get()` 按需读取。

技能的正文已经写出，有两个语言版本，且本仓库的 token 预算（见
[docs/TOKEN-BUDGET.md](../TOKEN-BUDGET.md)）要求「常驻增量控制在几百 token 量级」。

## 决定

**规范全文只放在技能里，系统提示里只留一行目录条目**（`t('skill.summary')`）。
模型知道有这么一份规范，需要细节时自己打开。

同时，技能正文按 `currentLocale()` 动态返回：`en-US` 返回 `SKILL.md`，`zh-CN` 返回
`SKILL.zh.md`，**不注册成两个技能**。

## 后果

**好的后果**

- 常驻成本与规范长度**解耦**。规范从 200 行长到 2000 行，每轮付的还是那一行目录条目。
  实测常驻增量为 903 字符（`en-US`）/ 572 字符（`zh-CN`），估算 226 / 240 token，
  落在「几百 token」这一档。
- 规范是**按需**读的，于是它可以是完整的、带例子的、不妥协的文本——不需要为了省 token
  把它压成口号。这是「技能优先」真正的收益。
- 语言切换不需要重新注册：`get()` 每次调用都读当前 locale，且正文读取结果在 provider 内缓存。

**坏的后果**

- **模型可能不读**。系统提示里的内容无法被忽略，技能目录条目是可以的。缓解方式是
  `skill.summary` 写成行动指令（「在提交、建分支或改文档之前先读它」）而不是名词短语。
  必须承认：这比强制注入弱。
- 多一层间接：读一次技能就是一次额外的工具调用与一次上下文增长（当前正文体量见
  [docs/TOKEN-BUDGET.md](../TOKEN-BUDGET.md)）。
  在长会话里反复读同一份正文是不划算的，provider 的正文缓存只能管到进程内。

**中性后果**

- `SKILL.md` 与 `SKILL.zh.md` 必须保持章节数量与层级顺序一致，由 `pnpm ci:checks` 校验。
- 技能名与插件同名（`dsh-dev-workflow`），这是有意的：用户看到的名字只有一个。
- `docs/TOKEN-BUDGET.md` 成为一份活的文档——任何改动常驻内容的 PR 都应该重新跑
  `.dev-docs/_probe/tokens-3a.mjs` 并更新数字。

## 被否决的方案

| 方案 | 否决理由 |
| --- | --- |
| 规范全文放系统提示 | 每轮都付两万字符级别的成本，与本仓库的 token 预算直接冲突。而且它挤掉的是真正属于系统提示的内容（工具用法、环境事实） |
| 规范全文放工具描述 | 工具描述同样是每轮常驻。写进描述就等于写进系统提示，只是位置更隐蔽 |
| 把规范压缩成几十行塞进系统提示 | 压缩必然丢掉边界条件与例子，而规范的价值恰恰在边界条件上（「`--no-verify` 默认 `ask` 而不是 `deny`，因为它是逃生通道」这种句子压不掉）。压缩版还会和 SKILL.md 形成两个事实源，随后必然漂移 |
| 注册两个技能（英文一个、中文一个） | 目录条目会变成两行，模型还要自己选。而正文选哪一份取决于会话语言，不是模型该操心的事 |
| 用事件监听把规范按需塞进上下文 | 属于「事件轰炸」：模型没在提交的时候也会收到内容，且会让上下文随会话增长。违反「事件监听极简」原则 |
